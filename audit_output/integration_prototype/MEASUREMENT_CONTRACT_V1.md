# Measurement contract V1 — first Java/Python/iFogSim task

## Status and scope

This contract reconciles the implemented Python JSONL v1.0 protocol with the inspected classic iFogSim2 execution path. It is a design-and-evidence document, not a simulation result and not a modification to the simulator or RL model.

The proposed end-to-end definition is implementable: **creation** is the one-task emitter's call/receipt time at `CloudSim.clock()`; **completion** is arrival of that task's result tuple at one explicitly selected endpoint; `latency_ms = endpoint_arrival_clock - creation_clock`; a completed task meets its deadline when `latency_ms <= deadline_ms`; a failed task never meets it. Classic iFogSim has the relevant events, but it does not retain this per-task record or implement deadlines itself. The experiment must add an adapter-owned task record and terminal observer.

All simulation-clock values are reported in the model's millisecond convention. This is supported by the DCNS example comment on `setUplinkLatency(100)` ("100 ms") and by the protocol's `*_ms` fields; the simulator type itself is `double` and does not enforce a unit.

## Event and correlation facts

`Sensor.transmit` creates an initial `Tuple`, sets its `actualTupleId` from `Sensor.updateTimings`, and schedules `FogEvents.TUPLE_ARRIVAL`. `FogDevice.processTupleArrival` routes or executes it. `FogDevice.executeTuple` calls `TimeKeeper.tupleStartedExecution`; `checkCloudletCompletion` calls `tupleEndedExecution` and produces resultant tuples. `Application.getResultantTuples` copies `actualTupleId` to resultant tuples. This supports a task registry keyed by the adapter `task_id` and linked to both ids.

`FogDevice.sendUpFreeLink` and `sendDownFreeLink` use `Tuple.getCloudletFileSize()` and the corresponding bandwidth to schedule actual transfers. They are the correct hooks for link-byte accounting. `NetworkUsageMonitor.sendingTuple(latency, tupleNwSize)` instead aggregates `latency * tupleNwSize` globally and cannot be converted into a per-task byte total.

## Timeout and fallback boundary

The proposed 1000 ms is a **wall-clock Java/Python response timeout**, not an iFogSim simulation-clock deadline. It is not yet exercised by a Java client. A persistent `ProcessBuilder` subprocess can be started before `CloudSim.startSimulation`; Java must write one UTF-8 JSONL observation, read one line with a bounded future/deadline, drain stderr concurrently, and terminate/close it during shutdown. A blocking read occurs while simulation time is not advancing, which is acceptable only for this one-task synchronous experiment and must be traceable.

If no valid action arrives by 1000 ms, on process exit, malformed JSON, or task-id/action mismatch, record `decision_source=fallback_timeout` or `fallback_error`, execute the approved Edge fallback only if the Edge target is available, and **do not send an outcome** for that task. There is then no valid Python pending decision. A valid action later overridden by an actual routing constraint is different: record the override and truthful `action_executed` before reporting its outcome.
