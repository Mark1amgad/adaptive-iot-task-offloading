## 1. Executive summary

The work moved the project from multi-task lifecycle fixtures and partial-offloading feasibility checks to a complete **nine-action V2 Python–Java–iFogSim execution path**, parameterized execution overheads, deterministic variable workloads, and paired multi-policy evaluation on three held-out synthetic workloads.

The main technical outcomes were:

1. Implemented an isolated V2 masked tabular learning protocol, keeping V1 separate.
2. Defined and integrated nine Local / Edge / Cloud full and partial actions.
3. Executed partial tasks as two real branches followed by a real merge Cloudlet, with task-level barriers and failure handling.
4. Made partition/merge overhead, deadline, WAN latency, and watchdog settings configurable and traceable.
5. Added deterministic seeded workloads with per-task compute, input/output size, deadlines, splittability, merge demand, and arrival gaps.
6. Expanded the learner state to 13,122 states and 118,098 Q-values.
7. Ran one 60-task training workload and three held-out 60-task paired evaluations, comparing Local, Edge Full, Cloud Full, Random, and frozen V2 policy.
8. Preserved run traces, model files, summaries, and audit outputs under `audit_output/`.

**Critical interpretation:** The held-out numbers are descriptive results for a fallback/greedy hybrid, not proof of learned RL superiority. The training model updated only 60 state-action cells; only 45 unique states were visited. On the 180 held-out decisions, 108 used the configured fallback action. This limitation is central and must be disclosed.

## 2. Research and implementation scope

The research direction remains adaptive execution/offloading across **Local, Edge, and Cloud** in an IoT–Edge–Cloud continuum. The implementation work in this session focused on making the action space executable and testable in iFogSim, rather than claiming that the research question has already been solved.

### Scope actually implemented

- A Python V2 policy server and protocol.
- A Java client/integration experiment running against iFogSim.
- Full placement and divisible partial placement.
- Feasibility masks computed for each task.
- Task lifecycle accounting, branch synchronization, merge execution, outcomes, and watchdog handling.
- Synthetic seeded workload generation and deterministic replay.
- Baseline and frozen-policy evaluation.
- Trace validators and reproducible PowerShell runners.

### Scope not yet implemented or established

- A realistic multi-IoT / multi-Edge topology; the current simulation is still a simple Local → Edge → Cloud hierarchy.
- Energy measurement.
- Empirical calibration of partition and merge costs.
- Validation of the proportional data-parallel partition model against a concrete application.
- Adequate tabular state/action coverage, convergence, statistically supported superiority, or generalization to other workload regimes.

### Stage H — Parameterizing execution overhead and timing controls

**Goal:** Remove hard-coded experiment timing values so that overhead assumptions can be swept and traced.

New Java / PowerShell parameters:
- `--partition-overhead-ms` / `-PartitionOverheadMs` (default 3.0 ms)
- `--merge-overhead-ms` / `-MergeOverheadMs` (default 2.0 ms)

- `--wan-latency-ms` / `-WanLatencyMs` (default 45 ms)

The watchdog is an execution horizon for unresolved work; it is not the same thing as the per-task deadline.

Sensitivity cases:
| Scenario | Partition | Merge |
|---|---:|---:|
| Zero | 0 ms | 0 ms |
| Nominal | 3 ms | 2 ms |
| High | 10 ms | 10 ms |

Each scenario covered all nine exact actions, a 30-task live learner integration episode, and the dropped-branch failure case. A floating-point comparison tolerance of 1e-9 ms was added for simulator timestamp representation.

Evidence:

### Stage I — Deterministic variable workload generation

**Goal:** Replace one fixed task profile with reproducible per-task variation.

Added:
- `generate_workload_v2.py`
- `run_v2_workload_smoke.ps1`
- `test_generate_workload_v2.py`
- `validate_v2_workload.py`
- Variable-workload acceptance documentation.

Supported profiles:
- `mixed`
- `divisible`
- `indivisible`

The mixed generator produces approximately 70% divisible and 30% indivisible tasks. Each generated JSONL task includes a sequence number, source seed, profile, compute demand, input/output payload sizes, deadline/urgency metadata, splittability, partition model, merge MI, and arrival gap.

Generator ranges:
| Property | Generated values |
|---|---|
| Compute | Uniform integer 1,000–30,000 MI |
| Input payload | Uniform integer 1,024–262,144 bytes |
| Output payload | 512, 2,048, or 8,192 bytes |
| Critical deadline | 90–180 ms |
| High deadline | 180–400 ms |
| Normal deadline | 400–1,000 ms |
| Merge compute | 4–12% of task MI for divisible tasks; zero otherwise |
| Arrival gap | First task 0 ms; later gaps 1–20 ms |

A local seeded PRNG makes the workload rows deterministic for the same seed, task count, and profile.

### Stage L — Auditing the actual contribution of the learned table

**This audit materially changes how the evaluation must be described.**

Direct inspection of the saved seed-42 model and held-out traces showed:
| Coverage measure | Result |
|---|---:|
| State space | 13,122 |
| Q-table entries | 118,098 |
| Training decisions / updates | 60 / 60 |
| Unique visited states | 45 (0.343% of states) |
| Unique updated state-action cells | 60 (0.0508% of table) |
| Maximum visits to any updated state-action cell | 1 |
| Held-out fallback decisions | 108 / 180 |
| Held-out greedy decisions | 72 / 180 |
| EDGE_FULL fallback selections | 108 |
| Total EDGE_FULL selections | 114 |

All 108 fallback decisions selected `EDGE_FULL`, the first feasible action in the configured fallback order. Only six of the 114 Edge Full choices came from greedy Q-table selection.

Therefore, the evaluated controller is best described as a **sparse Q-table plus deterministic fallback hybrid**. The performance table is real simulator output, but it cannot be used to claim that a well-trained RL policy learned a superior strategy. The current model has extremely sparse coverage and no repeated sample for any updated state-action cell.

## 7. Known limitations and research risks

1. **Sparse tabular coverage:** 60 training decisions update only 60 of 118,098 Q cells; 45 unique states are visited. This is the most immediate algorithmic limitation.
2. **Fallback dominates held-out decisions:** 108/180 evaluation decisions use `EDGE_FULL` fallback. Results must be labelled as a fallback/greedy hybrid.
3. **One training seed:** Only one model was trained (seed 42).
4. **Only three held-out seeds:** They come from the same synthetic generator distribution; this is not a new workload regime.
5. **No uncertainty estimates:** No paired confidence intervals, bootstrap intervals, effect-size analysis, or hypothesis tests have been reported.
6. **Synthetic workload:** Generator distributions are experiment settings, not measured real-world application distributions.
7. **Partition model assumption:** Input and output bytes scale proportionally with compute fraction; application-specific partition behavior may differ.
8. **Provisional overheads:** 3 ms partition and 2 ms merge are defaults, not empirically calibrated measurements.
9. **Simple topology:** Current simulation uses Local → Edge → Cloud, not multiple IoT devices and multiple Edge nodes.
10. **No energy metric:** Bandwidth is reported, but energy is not.
11. **Urgency metadata:** `urgency_class` is kept in workload/trace metadata, while the learner sees deadline bands rather than a separate urgency feature.
12. **Deadline calibration:** The 180/400 ms thresholds align with the synthetic generator's bands and need recalibration for real workloads.

## 8. Immediate next steps when work resumes

Recommended order:

1. **Do not immediately increase task count blindly.** First inspect the state encoder, feasible action masks, exploration schedule, Q update rule, and fallback behavior.
2. Design a state representation that can be learned with available data: coarser defensible bins, structured features, or a justified function approximator. Preserve interpretability and avoid unnecessary RL complexity.
3. Run enough independent training episodes/seeds to obtain repeated state-action visits. Track unique states, state-action coverage, visit-count distributions, action counts, and fallback fraction per episode.
4. Keep training seeds strictly separate from evaluation seeds. Train multiple independent models and evaluate each on paired held-out workloads.
5. Report paired uncertainty intervals and effect sizes; separate greedy decisions from fallback decisions.
6. Test held-out workload regimes (e.g. different arrival rates, payload distributions, divisible-task proportions, deadlines, and network conditions), not just new seeds from the same distribution.
7. Calibrate partition and merge costs against a concrete workload or defensible measurements; test whether proportional payload partition is valid.
8. Add energy measurement and expand topology to multiple IoT sources / Edge nodes when the current single-chain model is stable.
9. Re-run the full test suite and all relevant validators after code changes. Record exact commands, commit hashes, and output folders.
